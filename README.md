# SNP Anonymizer

Локальное Windows-приложение для обезличивания данных In.Plan SNP. Работает без Python на пользовательской машине; файловый режим полностью offline (без PostgreSQL, Docker и сети). Опционально — загрузка обезличенного датасета в указанный вами PostgreSQL (см. «Загрузка в PostgreSQL»). Интерфейс оформлен по дизайн-системе In.Plan (канонические токены: Open Sans, брендовый фиолетовый #9000ff, canvas #f5f6f8); вендоренные токены и логотип — `src/anonymizer/resources/ds/`, перегенерируются из архива DS (см. PROVENANCE.txt).

## Запуск

Откройте `dist/SNP-Anonymizer.exe`. Выберите SQL-файл или папку CSV, **новую** папку результата, локальный проект `.snpanon` и отрасль. Нажмите «Обезличить и экспортировать».

При повторной выгрузке того же клиента выберите прежний проект и ту же отрасль. Уже известные коды и названия получат прежние замены. Разные клиенты должны использовать разные проекты. Имена исходных схем входят в пространство замен: если клиент сменил имя схемы, это отдельное пространство.

Проект `.snpanon` — SQLite с исходными значениями и соответствиями. Он хранится отдельно от результата, не включается в пакет и не должен передаваться получателю обезличенных данных. Файл не зашифрован.

По желанию карта замен («что на что изменено»: домен, исходное значение, замена) выгружается в **отдельный Excel-файл** по явно указанному пути — в GUI строка «Карта замен в Excel», в CLI `--mapping-xlsx путь`. Файл всегда создаётся вне папки результата и содержит исходные значения: обращение с ним — как с проектом, получателям данных его не передавать. Значения записываются текстом, включая строки, начинающиеся с `=`. Ошибка подготовки Excel отменяет обработку до подключения к PostgreSQL; пакет не публикуется.

## Результат

| Файл | Назначение |
|---|---|
| `dump.sql` | Самостоятельный PostgreSQL SQL: схемы, `CREATE TABLE`, данные `COPY` |
| `inserts.sql` | Только данные; таблицы целевой схемы должны уже существовать |
| `csv/<схема>/<таблица>.csv` | UTF-8, запятая, заголовок; данные того же обработанного набора |
| `csv/manifest.json` | Структура, типы, имена файлов и формат NULL для CSV |
| `report.json` | Версия модели, число строк, правила полей, проверки и предупреждения |

Исходные схемы получают имена `snp_a000001`, `snp_a000002` и т. д. Технические имена таблиц и колонок сохраняются. `sys_id` исключается из CSV, списков COPY и INSERT; в DDL дампа это `bigint GENERATED BY DEFAULT AS IDENTITY`. Связи через `sys_id` блокируют экспорт: простое исключение поля разрушило бы эти ссылки.

Дамп восстанавливает таблицы и данные. Он не является полной резервной копией приложения: исходные функции, триггеры, владельцы, права, индексы, ограничения и DEFAULT не переносятся. Исходные комментарии SQL также исключаются. Это отражено в отчёте.

## Правила обезличивания

- Бизнес-коды заменяются по доменам сущностей; master и FK получают согласованные значения. Числовые идентификаторы и UUID поддерживаются, `sys_id` не заполняется.
- Названия товаров, площадок, ресурсов, КИП и каналов получают вымышленные подписи. Отрасли: пищевое производство, напитки, химия, потребительские товары, машиностроение. Замена не перестраивает BOM и не меняет технологические коэффициенты.
- Остальные клиентские тексты, в том числе бренды, категории, адреса, планировщики и комментарии данных, заменяются. Пустые строки и NULL сохраняются.
- Количества, цены, даты, булевы значения и технические числовые классификаторы сохраняются. Стандартные единицы измерения, флаги и ABC/XYZ сохраняются по явному списку в коде.
- В JSON заменяются текстовые значения и нестандартные имена свойств. Числа сохраняются без `float`, ISO-даты и структура сохраняются. Стандартные структурные ключи JSON сохраняются; ссылки `item/loc/res/comp` используют карты сущностей. JSON в ключах таблиц требует отдельного профиля и блокирует обработку. Форма значения нормализуется как `jsonb` (компактный вывод, декодирование `\u`, схлопывание повторных свойств); формальный профиль — в [input-contract.md](docs/input-contract.md). JSONB возможен только из SQL-входа: в снимке модели JSONB-колонок нет.

Проверки сравнивают число строк, сохраняемые поля и числа/даты JSON, дубликаты бизнес-ключей, доступные FK до/после. Составные FOREIGN KEY проверяются целыми кортежами, а не по отдельным колонкам; любая NULL-компонента исключает ссылку (MATCH SIMPLE). Каждая исходная PK/UNIQUE группа проверяется отдельно, включая составные; NULL в ключе не создаёт дубликата (PostgreSQL `NULLS DISTINCT`), `NULLS NOT DISTINCT` поддерживается, а NULL в PK-колонке отсекается раньше как NULL в обязательном поле (PK подразумевает NOT NULL). Группа ключей, содержащая `sys_id`, из проверки исключается: он не входит в выдачу и перегенерируется. Логический бизнес-ключ модели (YAML-флаги без группировки) проверяется отдельной группой с явно перечисленными колонками в отчёте. Исходные нарушения FK и дубликаты показываются в отчёте до и после (`missing_before`/`missing_after`, `extra_rows_before`/`extra_rows_after`); отсутствующий во входе master отмечается как непроверенный. Приложение не исправляет исходные дефекты данных. Проверки выполняются локально без загрузки в PostgreSQL.

Опция «Пропускать таблицы с ошибками» (галка в GUI / `--skip-error-tables`) продолжает обработку при табличных ошибках входа: битый CSV-файл или COPY/INSERT-блок пропускается целиком (гранулярность — таблица, частичные строки вычищаются). Пропущенные таблицы перечислены в `report.json` (`skipped_tables`) и в журнале с причиной. Ошибка загрузки любой таблицы в PostgreSQL откатывает весь набор, включая очистку таблиц; эта настройка не разрешает частичную загрузку в базу. Ошибки замены значений и расхождения ссылочной целостности остаются фатальными при любой настройке — это признаки неверной обезлички, а не дефект данных.

## Входной контракт

**SQL:** обычный `pg_dump` с `CREATE TABLE` и `COPY ... FROM stdin` в стандартном текстовом формате либо `INSERT ... VALUES` с литералами. Поддерживаются многострочные INSERT, quoted identifiers, `E''`, dollar quoting, inline и `ALTER TABLE ADD` PK/FK/UNIQUE (включая составные и `NOT VALID`), комментарии. `MATCH SIMPLE` действует по умолчанию; `MATCH FULL/PARTIAL` и `UNIQUE INCLUDE` отклоняются до обработки. SQL не исполняется. Неподдерживаемые конструкции завершают обработку с номером строки, без значений клиентских данных.

**ZIP:** источник может быть ZIP-архивом. Внутри — CSV-набор (плоско в корне или в одной подпапке, с опциональным manifest.json) либо ровно один `.sql`-дамп; смешанное содержимое и несколько дампов отклоняются. Посторонние файлы (прочие расширения, `__MACOSX`, dotfiles) игнорируются, но учитываются в лимите. Распаковка — в приватный временный каталог (удаляется после обработки/отмены): пути entries проверяются на zip-slip, суммарный несжатый объём ограничен 4 ГиБ с двойной защитой (по заголовкам и счётчиком при копировании).

Для data-only SQL типы берутся из снимка модели. Таблица без собственного DDL опознаётся по **бизнес-ключам эталона**: все BK-поля модели во входе — таблица обрабатывается, колонки вне эталона отбрасываются (в выдачу не входят, предупреждение в журнале — необезличиваемые данные не публикуются); хотя бы один BK отсутствует — таблица не опознана и пропускается целиком с причиной в журнале и `skipped_tables`; у эталона нет BK — применяется правило пересечения колонок. Отсутствие обязательных колонок модели блокирует обработку. Массивы, пользовательские SQL-типы, бинарный COPY, COPY CSV, INSERT-выражения, частичные UPDATE/DELETE, наследование таблиц и `standard_conforming_strings=off` не поддерживаются в версии 0.1.

**CSV:** одна таблица на файл, имена колонок в заголовке. Имя файла — техническое имя таблицы; хвост `_<12+ цифр>` удаляется. Автоопределение разделителя или выбор `;`, `,`, табуляции, `|`; UTF-8 и Windows-1251. NULL — явный токен `\N`, пустое поле — пустая строка. Для числового/датового NULL нужен `\N`, а не пустая строка. Переносы строк и кавычки обрабатываются стандартным CSV-парсером.

Снимок из `C:\Git\inplan-data-model`: 203 таблицы, версия 0.2.0, SHA и хеш YAML записаны в `resources/model.json` и отчёте. Примеры строк не включаются. Обычный CSV создаёт полную структуру соответствующей таблицы модели: отсутствующие необязательные колонки заполняются NULL; отсутствие обязательной колонки блокирует обработку. Для `NUMBER`, у которого в YAML не указана дробная точность, используется unconstrained `numeric`, чтобы не округлять клиентские значения. Физические типы SQL-входа сохраняются для поддерживаемых встроенных типов.

Выходные CSV можно снова прочитать через `manifest.json`: он восстанавливает типы и отличает NULL, пустую строку и буквальный `\N` (в этом случае начальный обратный слеш удваивается).

Размер отдельного поля/строки ограничен 8 МиБ. Буферы, кеш замен и промежуточные проверки ограничены байтами; строки хранятся на диске в SQLite. Потребуются место для исходного набора, промежуточной SQLite и всех трёх экспортов; размер зависит от числа уникальных значений. Временные данные удаляются после штатного завершения/отмены. При принудительном завершении процесса временные каталоги могут остаться в `%TEMP%` и рядом с папкой результата.

```powershell
.venv\Scripts\python.exe -m anonymizer --input C:\data\client.sql --output C:\data\anon_new --project C:\private\client.snpanon --industry chem
```

```powershell
C:\Git\inplan-data-model\.venv\Scripts\python.exe tools\snapshot_model.py C:\Git\inplan-data-model src\anonymizer\resources\model.json
```

## Загрузка в PostgreSQL

Необязательный шаг после обезличивания и всех проверок: датасет загружается в указанную целевую схему (типа `public_N`) вашего PostgreSQL. Сначала локально готовится Excel-карта, если она запрошена. Одна PG-транзакция: схема создаётся при отсутствии → проверяется наличие всех таблиц датасета (нет — отказ) → `TRUNCATE` только таблиц датасета одним оператором (`RESTART IDENTITY`, без CASCADE) → потоковый `COPY` из секций проверенного `dump.sql` (те же данные, что в файлах; `sys_id` генерирует identity) → запись отчёта, публикация Excel-карты, сохранение проекта и публикация пакета → фиксация PG. Ошибка или отмена до начала PG-фиксации откатывает загрузку целиком и убирает новый пакет. При поздней локальной ошибке уже сохранённые дополнительные соответствия проекта или Excel-карта могут остаться; повторный запуск использует сохранённые замены.

Файлы и PostgreSQL не образуют общую транзакцию. При потере подтверждения PG-фиксации приложение сообщает неопределённый исход и сохраняет пакет, проект и Excel-карту: требуется проверить целевые таблицы перед повторным запуском. Отмена после начала фиксации не гарантирует откат. Поле `pg_commit_status` в отчёте равно `not_confirmed` до подтверждения и `committed` после него. Если обновить локальный отчёт после успешной фиксации не удалось, загрузка считается успешной, журнал содержит предупреждение, а файл отчёта остаётся с `not_confirmed`.

В GUI — блок «Загрузка в PostgreSQL» (включается флажком; пароль не сохраняется). В CLI:

```powershell
.venv\Scripts\python.exe -m anonymizer --input C:\data\client.sql --output C:\data\anon_new --project C:\private\client.snpanon --pg-host db.internal --pg-db inplan --pg-user svc --pg-schema public_5
```

Пароль запрашивается скрыто, если не передан `--pg-password`. Целевые таблицы должны существовать (штатный сценарий — существующая схема In.Plan); приложение не создаёт таблицы и не изменяет схему, кроме `CREATE SCHEMA IF NOT EXISTS`. Подключение идёт только к указанному серверу; входной SQL не исполняется. Повторная загрузка с тем же проектом заменяет содержимое таблиц датасета, не добавляя дубликаты.

## Журнал проверок и ошибок

Каждый прогон ведёт журнал: стадии обработки, результат **каждой** проверки (составные FK и группы PK/UNIQUE с счётчиками «до→после», непроверенные связи, сверка сохраняемых полей), все ошибки и отмена. Журнал содержит только технические имена и счётчики — значений клиентов, путей источника и паролей в нём нет.

- **GUI:** кнопка «Выгрузить журнал (CSV)» внизу окна — активна после завершения прогона (и после успешного, и после неудачного/отменённого); путь выбирается в диалоге.
- **CLI:** `--log-csv путь` — журнал записывается в конце прогона (включая неуспешный).
- Формат: `;`-разделитель, UTF-8 with BOM (Excel открывает двойным кликом). Журнал — отдельный артефакт: в пакет результата и report.json он не входит.

## Проверка объёма

`tools/benchmark.py` создаёт синтетический COPY около 1 ГиБ и запускает импорт, обезличивание, проверки и все три экспорта. Измерение в [docs/benchmark-1gib.json](docs/benchmark-1gib.json): 306 345 строк, 211.04 с, пик RSS 52.7 МиБ. Во время измерения также выполнялись сборка EXE и тесты. Нагрузка содержит повторяющийся свободный текст; это не SLA и не измерение высокой кардинальности или огромного INSERT.

`tools/benchmark_composite.py` — синтетическая нагрузка составных FK с высокой кардинальностью (уникальные двухколоночные кортежи в parent и child). Замер в [docs/benchmark-composite-fk.json](docs/benchmark-composite-fk.json). `tools/benchmark_keys.py` — высокая кардинальность независимых UNIQUE-ключей. Замер в [docs/benchmark-key-groups.json](docs/benchmark-key-groups.json). Повторные прогоны 1 ГиБ после GLM-001 и GLM-002 — [docs/benchmark-1gib-glm001.json](docs/benchmark-1gib-glm001.json) и [docs/benchmark-1gib-glm002.json](docs/benchmark-1gib-glm002.json). Это отдельные измерения своих нагрузок, не сравнение с SLA и не замена исходного замера.
