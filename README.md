# SNP Anonymizer

Локальное Windows-приложение для обезличивания данных In.Plan SNP. Работает без Python на пользовательской машине; файловый режим полностью offline (без PostgreSQL, Docker и сети). Опционально — загрузка обезличенного датасета в указанный вами PostgreSQL (см. «Загрузка в PostgreSQL»). Интерфейс оформлен по дизайн-системе In.Plan (новый фирменный стиль: Manrope, синий #4769ff, тёмно-синий #04143a, фон #f4f6fa); вендоренные токены и логотип — `src/anonymizer/resources/ds/`, перегенерируются из архива DS (см. PROVENANCE.txt).

## Запуск

Скачайте [SNP-Anonymizer.exe: XLSX, обработка без эталона и профили связности](distrib/SNP-Anonymizer.exe) (на странице файла нажмите **Download raw file**). [Контрольная сумма SHA256](distrib/SNP-Anonymizer.exe.sha256). Исходный код приложения — в `src/anonymizer/`.

[Пошаговая инструкция в шаблоне In.Plan — PowerPoint, 14 слайдов](docs/SNP-Anonymizer-user-guide.pptx).

Откройте скачанный `SNP-Anonymizer.exe` (в копии репозитория — `distrib/SNP-Anonymizer.exe`). Выберите источник, **новую** папку результата, локальный проект `.snpanon` и отрасль. Нажмите «Обезличить и экспортировать».

Для нового проекта нажмите «Новый…» и выберите папку отдельно от входных данных и результата. Имя `.snpanon` назначается автоматически; создавать файл или вводить имя вручную не нужно. Приложение создаст файл при запуске обработки. «Открыть…» позволяет выбрать существующий проект.

При повторной выгрузке того же клиента выберите прежний проект и ту же отрасль. Уже известные коды и названия получат прежние замены. Разные клиенты должны использовать разные проекты. Имена исходных схем входят в пространство замен: если клиент сменил имя схемы, это отдельное пространство.

Проект `.snpanon` — SQLite с исходными значениями и соответствиями. Он хранится отдельно от результата, не включается в пакет и не должен передаваться получателю обезличенных данных. Файл не зашифрован.

По желанию карта замен («что на что изменено»: домен, исходное значение, замена) выгружается в **отдельный Excel-файл** по явно указанному пути — в GUI строка «Карта замен в Excel», в CLI `--mapping-xlsx путь`. Для профильных замен вместо внутренних хешей показаны домен, исходная схема и связанные поля, например «Ресурс производства (RESOURCE_PROD), схема public»; общий namespace обозначен отдельно. Файл всегда создаётся вне папки результата и содержит исходные значения: обращение с ним — как с проектом, получателям данных его не передавать. Значения записываются текстом, включая строки, начинающиеся с `=`. Ошибка подготовки Excel отменяет обработку до подключения к PostgreSQL; пакет не публикуется.

EXE в `distrib/` поддерживает импорт XLSX-файла, папки, смешанного CSV/XLSX ZIP, опциональную обработку без эталона и профили связности Optimizer/JSON. Для согласованных замен Optimizer выберите «Профиль связности → Optimizer v2»; по умолчанию профиль выключен. PowerPoint-инструкция описывает основные шаги работы; новые настройки связности приведены ниже и во встроенной справке (F1).

## Результат

| Файл | Назначение |
|---|---|
| `dump.sql` | Самостоятельный PostgreSQL SQL: схемы, `CREATE TABLE`, данные `COPY` |
| `inserts.sql` | Только данные; таблицы целевой схемы должны уже существовать |
| `csv/<схема>/<таблица>.csv` | UTF-8, запятая, заголовок; данные того же обработанного набора |
| `csv/manifest.json` | Структура, типы, имена файлов и формат NULL для CSV |
| `report.json` | Отчёт v2: версия модели/профиля, охват, результат проверок и исходные дефекты |
| `connectivity-profile.json` | Применённый профиль связности, если он выбран; без приватной карты замен |

Исходные схемы получают имена `snp_a000001`, `snp_a000002` и т. д. Технические имена таблиц и колонок сохраняются. `sys_id` присутствует в CSV и COPY полного дампа с NULL; в DDL это nullable `bigint` без identity. В data-only `inserts.sql` поле исключается из INSERT, чтобы существующая таблица могла назначить ID через default/identity. `update_date_time` сохраняется как прочитано, `change_author` заменяется на `snp`, включая NULL и пустые значения. Эти три поля не проверяются по типу, размеру, обязательности или ключам; PK/UK/FK с системной колонкой исключаются целиком.

Дамп восстанавливает таблицы и данные. Он не является полной резервной копией приложения: исходные функции, триггеры, владельцы, права, индексы, ограничения и DEFAULT не переносятся. Исходные комментарии SQL также исключаются. Это отражено в отчёте.

## Профили связности

В блоке настроек выберите **«Optimizer v2»** или **«JSON-файл…»**. Выбор профиля включает «Требовать проверенную связность»: набор выдаётся только после PASS всех обязательных проверок. Если снять этот флажок, допускается выдача с неполным охватом и отметкой `UNVERIFIED_INTEGRITY`; обнаруженный FAIL преобразования блокирует набор в любом режиме. По умолчанию выбран «Без профиля», а требование выключено.

Профиль работает и с галочкой «Обрабатывать без эталонной модели»: `model_applied=false`, дополнительные колонки сохраняются. Optimizer v2 согласует LOCATION, PRODUCT и BOM; TRANSPORT_TYPE и CLIENT остаются отдельными доменами. `supplier` использует ту же карту, что `location`/`loc_from`/`loc_to`. Namespace по умолчанию — исходная схема; проверки учитывают `datasetid` и объявленные ключи периодов.

Ресурсы производства, хранения и перевозки независимы. Поле `optimizer_production.resource` получает коды `resource_prod_000001`, `optimizer_storage.resource` — `resource_stock_000001`, а `optimizer_transportation.resource` — `resource_transp_000001`. Одинаковый исходный код в разных видах ресурсов не означает общий объект. Встроенный профиль требует текстовый тип и место для префикса, разделителя и минимум шести цифр. Числовой тип или недостаточная длина поля блокируют обработку; приложение не меняет тип и не отбрасывает префикс.

Для профиля используйте новый проект `.snpanon`. Формат профильного проекта остаётся v2 и хранит отпечаток эффективного контракта. Проект, созданный с прежним Optimizer v1 и общим доменом RESOURCE, не подходит для Optimizer v2: создайте новый файл. Автоматической миграции карт нет; прежний файл сохраняется. Команда `builtin:optimizer-v1` отклоняется с указанием нового профиля. Старые проекты без профиля продолжают работать по прежним правилам.

Профильные идентификаторы поддерживают текст, точные целые/десятичные числа и UUID. Идентификаторы FLOAT/REAL и явный COLLATE в домене блокируются с `CHECK_UNSUPPORTED`; обычные числовые показатели FLOAT/REAL сохраняются. Проверки отношений и ключей с FLOAT/REAL, JSON/JSONB, TIME/TIMESTAMP или явным COLLATE получают `UNSUPPORTED`. При требовании проверенной связности неподдерживаемая обязательная проверка оставляет только диагностику. Сравнение DATE учитывает календарную дату, включая компактную ISO-запись, без изменения исходного представления в выдаче; CHAR/CHARACTER без указанной длины означает один символ.

В `report.json` результат сохранения отношений (`integrity_status`) отделён от дефектов входа (`source_integrity_status`) и факта исполнения проверок (`relationships_checked`, `keys_checked`). `PASSED` относится к обязательному объявленному охвату, указанному в `coverage`, и не подтверждает выполнимость оптимизатора или совместимость с произвольной БД. Транзитный узел без спроса сам по себе не считается ошибкой. Даты и длительности сохраняются; вычисляемые правила прибытия в первой версии не проверяются.

В отчёте схемы пропущенных таблиц также обозначаются псевдонимами, без раскрытия исходных имён схем.

При FAIL, незавершённой проверке или невыполненном требовании связности создаётся только безопасный диагностический `report.json`: `dataset_published=false`, `publication_mode=null`. CSV/SQL и приватная карта в такой папке не публикуются, загрузка в PostgreSQL не начинается.

CLI: `--connectivity-profile builtin:optimizer-v2` либо `--connectivity-profile путь.json`; флаг `--require-integrity` требует полного обязательного PASS. [Формат JSON-профиля и примеры](docs/connectivity-profile.md).

## Правила обезличивания

Все новые текстовые замены используют ASCII-латиницу: например, `Milk chocolate - series 0001`, `North site 0001`, `Attribute 0001`. Это относится и к заменам строк/ключей JSON. Числа, даты, булевы, сохраняемые технические значения и `update_date_time` не транслитерируются; интерфейс остаётся русским.

Сохранённые ASCII-замены прежних проектов используются без изменений. Если нужна старая нелатинская замена, обработка безопасно прекращается с предложением создать новый `.snpanon`; прежняя карта не переписывается. При экспорте карты в Excel это правило проверяется и для исторических замен, включая неиспользованные в текущем входе.

- Бизнес-коды заменяются по доменам сущностей; master и FK получают согласованные значения. Числовые идентификаторы и UUID поддерживаются, `sys_id` не заполняется.
- Названия товаров, площадок, ресурсов, КИП и каналов получают вымышленные подписи. Отрасли: пищевое производство, напитки, химия, потребительские товары, машиностроение. Замена не перестраивает BOM и не меняет технологические коэффициенты.
- Остальные клиентские тексты, в том числе бренды, категории, адреса, планировщики и комментарии данных, заменяются. Пустые текстовые строки и NULL сохраняются.
- Количества, цены, даты, булевы значения и технические числовые классификаторы сохраняются. Стандартные единицы измерения, флаги и ABC/XYZ сохраняются по явному списку в коде.
- В JSON заменяются текстовые значения и нестандартные имена свойств. Числа сохраняются без `float`, ISO-даты и структура сохраняются. Стандартные структурные ключи JSON сохраняются; ссылки `item/loc/res/comp` используют карты сущностей. JSON в ключах таблиц требует отдельного профиля и блокирует обработку. Форма значения нормализуется как `jsonb` (компактный вывод, декодирование `\u`, схлопывание повторных свойств); формальный профиль — в [input-contract.md](docs/input-contract.md). JSONB возможен только из SQL-входа: в снимке модели JSONB-колонок нет.

Проверки заново читают фактические CSV, `dump.sql` и `inserts.sql`, сравнивают строки, сохраняемые значения и объявленные отношения. Составные FK проверяются целыми кортежами; NULL-семантика задаётся контрактом, включая `MATCH SIMPLE` и NULL-safe равенство. Для связей сравниваются точные потерянные/добавленные пары (`lost`/`added`), для каждого независимого PK/UNIQUE/BK — состав групп дублей. Равенства общих счётчиков недостаточно. Исходные дефекты сохраняются и отражаются отдельно. Отсутствующая цель, неподдерживаемая проверка и группа с системным полем не получают PASS; причины видны в coverage. Все проверки выполняются локально до опциональной загрузки PostgreSQL.

Опция «Пропускать таблицы с ошибками» (галка в GUI / `--skip-error-tables`) продолжает обработку при табличных ошибках входа: битый CSV-файл или COPY/INSERT-блок пропускается целиком (гранулярность — таблица, частичные строки вычищаются). Пропущенные таблицы перечислены в `report.json` (`skipped_tables`) и в журнале с причиной. Ошибка загрузки любой таблицы в PostgreSQL откатывает весь набор, включая очистку таблиц; эта настройка не разрешает частичную загрузку в базу. Ошибки замены значений и расхождения ссылочной целостности остаются фатальными при любой настройке — это признаки неверной обезлички, а не дефект данных.

## Обработка без эталонной модели

Включите «Обрабатывать без эталонной модели» в настройках либо передайте CLI `--bypass-model`. Режим применяется ко всем таблицам выбранного входа: известным, неизвестным и дополнительным колонкам. По умолчанию галочка выключена и действуют прежние правила эталона.

CSV/XLSX получают структуру из заголовка и типов всех непустых значений, без выборки первых строк; SQL и CSV с manifest — из входного описания типов. Для SQL без DDL режиму нужно описание структуры, угадывания по эталону нет. В XLSX учитываются реальные типы ячеек и форматы дат Excel; текстовые коды, включая `001` и `123`, остаются текстом. В CSV даты и время распознаются в ISO-формате, ведущие нули сохраняют текстовый тип; в XLSX текстовые ячейки остаются текстом, даже если похожи на дату. Пустоты в определённых числовых, датовых, логических и UUID-колонках становятся NULL; полностью пустая колонка остаётся TEXT. При несовместимых непустых типах одной колонки обработка таблицы завершается безопасной ошибкой вместо изменения чисел.

Без профиля все непустые обычные тексты заменяются, включая единицы измерения, ABC/XYZ и текстовые флаги. Числа, булевы и даты сохраняются; **числовые идентификаторы также сохраняются**. `sys_id` очищается до NULL; `update_date_time` сохраняется как прочитано; `change_author` становится `snp`. Связи и ключи не определяются и не проверяются; замены текста независимы для разных колонок. Это отмечено в `report.json` (`model_applied=false`, `structure_mode=automatic_without_model`, `relationships_checked=false`, `keys_checked=false`). При выбранном профиле общие домены и проверки применяются отдельно, включая замену явно объявленных числовых идентификаторов числовыми кодами.

Без профиля новые текстовые замены содержат имя колонки: `product_000001`, `resource_000001`, `location_000001`, `bomnum_000001`. Это подписи для различимости, а не определение связей между таблицами. Если длина поля не позволяет вместить подпись, используется прежний компактный код. Уже сохранённые в проекте замены не меняются: чтобы заменить прежние «Атрибут 0001» новым форматом, создайте новый `.snpanon`. Новые значения в прежнем проекте получают новый формат со следующего номера. Правила UUID и содержимого JSON не меняются.

Режим использует отдельные домены замен в том же локальном проекте: повторный запуск стабилен, старые соответствия стандартного режима не подмешиваются. Автоопределение и повторное чтение выполняются через временный SQLite-спул с ограниченной памятью; исходные файлы не меняются. Общий каталог таблиц ограничен 16 МиБ, структура одной таблицы — 16 384 колонками; CSV-запись, manifest и собираемые SQL-метаданные ограничиваются до накопления. Превышение общего лимита прекращает весь прогон, даже при включённом пропуске таблиц.

## Входной контракт

**SQL:** обычный `pg_dump` с `CREATE TABLE` и `COPY ... FROM stdin` в стандартном текстовом формате либо `INSERT ... VALUES` с литералами. Поддерживаются многострочные INSERT, quoted identifiers, `E''`, dollar quoting, inline и `ALTER TABLE ADD` PK/FK/UNIQUE (включая составные и `NOT VALID`), комментарии. `MATCH SIMPLE` действует по умолчанию; `MATCH FULL/PARTIAL` и `UNIQUE INCLUDE` отклоняются до обработки. SQL не исполняется. Неподдерживаемые конструкции завершают обработку с номером строки, без значений клиентских данных.

**ZIP:** внутри — CSV/XLSX-набор в корне либо одной общей подпапке или ровно один `.sql`-дамп. CSV и XLSX разных таблиц можно сочетать. SQL вместе с табличными файлами и несколько дампов отклоняются. Посторонние расширения, `__MACOSX` и dotfiles игнорируются, но учитываются в лимите. Распаковка — в приватный временный каталог с проверкой zip-slip и двойным ограничением 4 ГиБ (заголовки и фактически прочитанные байты). Число записей ZIP ограничено 4096, каталог ZIP — 8 МиБ; ZIP64-каталог не поддерживается. Временные данные удаляются после обработки/отмены.

Для data-only SQL типы берутся из снимка модели. Таблица без собственного DDL опознаётся по **бизнес-ключам эталона**: все BK-поля модели во входе — таблица обрабатывается, колонки вне эталона отбрасываются (в выдачу не входят, предупреждение в журнале — необезличиваемые данные не публикуются); хотя бы один BK отсутствует — таблица не опознана и пропускается целиком с причиной в журнале и `skipped_tables`; у эталона нет BK — применяется правило пересечения колонок. Отсутствие обязательных колонок модели блокирует обработку. Массивы, пользовательские SQL-типы, бинарный COPY, COPY CSV, INSERT-выражения, частичные UPDATE/DELETE, наследование таблиц и `standard_conforming_strings=off` не поддерживаются в версии 0.1.

**CSV:** одна таблица на файл, имена колонок в заголовке. Имя файла — техническое имя таблицы; хвост `_<12+ цифр>` удаляется. Автоопределение разделителя или выбор `;`, `,`, табуляции, `|`; UTF-8 и Windows-1251. NULL — явный токен `\N`. Во внешнем CSV без `manifest.json` пустая ячейка (включая `""`) в необязательном поле `NUMBER`/`INTEGER` также означает NULL. Непустые числа сохраняются без изменения, пустота не заменяется нулём. В текстовых полях пустая ячейка остаётся пустой строкой; пробелы и обязательные поля не нормализуются. Для датового NULL нужен `\N`. В CSV с manifest пустая ячейка означает NULL только в колонках, явно перечисленных в `tables[].empty_null_columns`; без этого списка сохраняются прежние правила: NULL — `\N`, пустая ячейка — пустая строка. Переносы строк и кавычки обрабатываются стандартным CSV-парсером.

Снимок из `C:\Git\inplan-data-model`: 203 таблицы, версия 0.2.0, SHA и хеш YAML записаны в `resources/model.json` и отчёте. Примеры строк не включаются. Обычный CSV создаёт полную структуру соответствующей таблицы модели: отсутствующие необязательные колонки заполняются NULL; отсутствие обязательной колонки блокирует обработку. Для `NUMBER`, у которого в YAML не указана дробная точность, используется unconstrained `numeric`, чтобы не округлять клиентские значения. Физические типы SQL-входа сохраняются для поддерживаемых встроенных типов.

**XLSX:** один файл на таблицу, имя файла задаёт таблицу по тем же правилам, что CSV; внутри ровно один лист с произвольным именем. Строка 1 содержит технические имена колонок. Выбирайте отдельный `.xlsx`, папку или ZIP с CSV/XLSX. Повтор одной таблицы в нескольких файлах блокирует набор; XLSX вместе с `manifest.json` не поддерживается. Папка содержит не более 4096 табличных файлов.

Скрытые и отфильтрованные строки XLSX читаются; полностью пустые строки пропускаются. Отсутствующая ячейка — NULL, явно пустой текст остаётся пустым текстом; пустая строка в необязательном NUMBER/INTEGER — NULL. Токен `\N` означает NULL. Формулы (даже с сохранённым результатом), Excel-ошибки и объединённые ячейки в области таблицы отклоняются. Пропуск таблиц с ошибками применяется ко всей книге, включая уже прочитанные строки; глобальные лимиты и неоднозначный состав набора блокируют прогон.

Числа XLSX читаются без `float` и округления; формат отображения Excel не применяется. Коды с ведущими нулями нужно хранить текстом. Округление, уже сделанное Excel при сохранении числа, восстановить нельзя. Для полей DATE/DATE_TIME/TIME поддерживаются ISO и числовые даты Excel 1900/1904; фиктивное 29.02.1900 и значения с потерей точности отклоняются. Формулы не вычисляются, внешние источники не запрашиваются. `.xls`, `.xlsb`, `.xlsm`, защищённые книги и выбор листов не поддерживаются. Параметр CLI `--csv-schema` задаёт исходную схему также для XLSX; настройки кодировки и разделителя действуют только на CSV.

Выходные CSV можно снова прочитать через `manifest.json`: он восстанавливает типы и отличает NULL, пустую строку и буквальный `\N` (в этом случае начальный обратный слеш удваивается).

В выходном CSV числовой NULL (включая очищенный `sys_id`) записывается пустой ячейкой. В режиме без эталона так же выводятся колонки, содержащие только NULL: их тип не угадывается по имени. Эти колонки отмечаются в `empty_null_columns`; храните CSV вместе с manifest для точного повторного импорта. Пустой TEXT и смешанные NULL/пустые строки сохраняют прежнее различение. `update_date_time` сохраняет исходное представление, включая различие NULL и пустой строки. SQL-дамп и PostgreSQL COPY используют штатный маркер NULL `\N`, INSERT — `NULL`.

Новый CSV-пакет имеет формат `snp-anonymizer-csv-v2`; для его повторного импорта нужен обновлённый EXE. Старые пакеты `v1` по-прежнему читаются по прежним правилам. SQL не меняется; профильные проекты и отчёт связности используют версии v2, описанные выше.

Размер отдельного поля/строки ограничен 8 МиБ. Буферы, кеш замен и промежуточные проверки ограничены байтами; строки хранятся на диске в SQLite. Потребуются место для исходного набора, промежуточной SQLite и всех трёх экспортов; размер зависит от числа уникальных значений. Временные данные удаляются после штатного завершения/отмены. При принудительном завершении процесса временные каталоги могут остаться в `%TEMP%` и рядом с папкой результата.

## Загрузка в PostgreSQL

Необязательный шаг после обезличивания и всех проверок: датасет загружается в указанную целевую схему (типа `public_N`) вашего PostgreSQL. Сначала локально готовится Excel-карта, если она запрошена. Одна PG-транзакция: схема создаётся при отсутствии → проверяется наличие всех таблиц датасета (нет — отказ) → `TRUNCATE` только таблиц датасета одним оператором (`RESTART IDENTITY`, без CASCADE) → потоковый `COPY` из секций проверенного `dump.sql` (те же бизнес-данные, что в файлах; очищенный `sys_id` не передаётся, его назначает целевая БД) → запись отчёта, публикация Excel-карты, сохранение проекта и публикация пакета → фиксация PG. Ошибка или отмена до начала PG-фиксации откатывает загрузку целиком и убирает новый пакет. При поздней локальной ошибке уже сохранённые дополнительные соответствия проекта или Excel-карта могут остаться; повторный запуск использует сохранённые замены.

Файлы и PostgreSQL не образуют общую транзакцию. При потере подтверждения PG-фиксации приложение сообщает неопределённый исход и сохраняет пакет, проект и Excel-карту: требуется проверить целевые таблицы перед повторным запуском. Отмена после начала фиксации не гарантирует откат. Поле `pg_commit_status` в отчёте равно `not_confirmed` до подтверждения и `committed` после него. Если обновить локальный отчёт после успешной фиксации не удалось, загрузка считается успешной, журнал содержит предупреждение, а файл отчёта остаётся с `not_confirmed`.

В GUI — блок «Загрузка в PostgreSQL» (включается флажком; пароль не сохраняется). В CLI:

```powershell
.venv\Scripts\python.exe -m anonymizer --input C:\data\client.sql --output C:\data\anon_new --project C:\private\client.snpanon --pg-host db.internal --pg-db inplan --pg-user svc --pg-schema public_5
```

Пароль запрашивается скрыто, если не передан `--pg-password`. Целевые таблицы должны существовать (штатный сценарий — существующая схема In.Plan); приложение не создаёт таблицы и не изменяет схему, кроме `CREATE SCHEMA IF NOT EXISTS`. Подключение идёт только к указанному серверу; входной SQL не исполняется. Повторная загрузка с тем же проектом заменяет содержимое таблиц датасета, не добавляя дубликаты.

## Журнал проверок и ошибок

Каждый прогон ведёт журнал: стадии обработки, результат **каждой** проверки (составные FK и группы PK/UNIQUE с счётчиками «до→после», непроверенные связи, сверка сохраняемых полей), все ошибки и отмена. Журнал содержит только технические имена и счётчики — значений клиентов, путей источника и паролей в нём нет.

- **GUI:** кнопка «Выгрузить журнал (CSV)» внизу окна — активна после завершения прогона (и после успешного, и после неудачного/отменённого); путь выбирается в диалоге.
- **CLI:** `--log-csv путь` — журнал записывается в конце прогона (включая неуспешный).
- Формат: `;`-разделитель, UTF-8 with BOM (Excel открывает двойным кликом). Журнал — отдельный артефакт: в пакет результата и report.json он не входит.
