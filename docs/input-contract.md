# Контракт входов и сохранения данных

Контекст: 13.10.2026, offline SNP Anonymizer 0.1.0. Клиентские данные не использованы при разработке. Физический SQL-каталог извлекается из входа; для CSV и data-only INSERT используется замороженный metadata-only снимок YAML.

Источник снимка: `inplan-data-model` 0.2.0, Git `af72e43a322f1ee7f7d8b2d930cc8cf3b99e970e`. Хеш содержимого и 203 таблицы — в `src/anonymizer/resources/model.json`. Снимок построен `tools/snapshot_model.py`; примеры, descriptions и клиентские значения не включены. Автоматическая совместимость с любым физическим стендом не предполагается.

| Слой | Идентичность и зерно |
|---|---|
| Вход | SQL-файл, CSV-папка или ZIP-архив (CSV-набор плоско/в одной подпапке либо один SQL-дамп; zip-slip и распаковка свыше 4 ГиБ запрещены); схема и техническое имя таблицы |
| Физическая строка | Порядковый id внутренней SQLite; не клиентский sys_id |
| Бизнес-ключ | Поля BK/PK/UK модели и исходного DDL; каждая PK/UNIQUE группа DDL проверяется отдельно; логический BK модели — отдельной группой с явным grain (колонки в отчёте); числовые идентификаторы отдельно от количеств |
| Ссылка | Имена source/target колонок из FK модели либо исходного DDL, включая схему; составные FK сохраняются упорядоченными группами и проверяются целыми кортежами |
| Проект | Отрасль, секрет для UUID, локальная таблица домен/старое/новое/порядковый номер |
| Замена | Домен исходной схемы и конечного master-поля; одинаковый исходный код в item и loc — разные сущности |

Вход читается без изменения. SQL-команды не выполняются. Приложение не подключается к БД, кроме явно включённой опциональной загрузки результата (см. «Загрузка в PostgreSQL» ниже): подключение только к указанному пользователем серверу, только сгенерированный workload. Таблица без DDL опознаётся по бизнес-ключам эталона: все BK во входе — обрабатывается с отбрасыванием колонок вне эталона (предупреждение в журнале; необезличиваемые данные не публикуются); BK не совпали — таблица пропускается целиком (skipped_tables/журнал, не ошибка прогона); отсутствие обязательных колонок модели блокирует обработку. Схемы можно ограничить явно; пустой список означает все схемы. Неподдерживаемый тип в незадействованной схеме всё равно может блокировать импорт: весь SQL должен быть синтаксически понятен reader.

Числа хранятся строками и Decimal при проверке, JSON-числа — исходными лексемами. NULL, пустая строка, ноль и отсутствующая колонка различаются. Пропущенная обязательная колонка с DEFAULT в INSERT не вычисляется и блокирует обработку. Системные даты остаются датами. UUID перегенерируются по проекту с общим доменом ссылок.

Исключение при чтении внешнего CSV без `manifest.json` (16.10.2026, `anonymizer-pav`): пустая ячейка, включая `""`, в nullable-поле `NUMBER`/`INTEGER` интерпретируется как NULL до проверок и обезличивания. Ноль и непустые числа сохраняются точно, пробелы не удаляются. Пустой TEXT, обязательные поля, даты и SQL используют прежние правила; явный токен `\N` остаётся обозначением NULL. Нормализация выполняется потоково по метаданным таблицы и не меняет исходный файл.

CSV-выдача (29.10.2026, `anonymizer-1as`): NULL в `NUMBER`/`INTEGER`, включая `sys_id`, записывается пустой ячейкой. Без эталона полностью NULL-колонки с неопределённым типом тоже выводятся пустыми: тип остаётся TEXT, по имени ничего не угадывается. В каждой записи `manifest.tables[]` опциональный список `empty_null_columns` объявляет имена колонок, где пустая ячейка означает NULL. Список ограничен физическими колонками, имена уникальны; некорректный список отклоняется безопасно. Без списка сохраняется прежний manifest-контракт (NULL только `\N`). Пустой TEXT, смешанные пустые строки/NULL, буквальный `\N` и экранирование ведущего слеша различаются как прежде. `update_date_time` не переводится на этот кодек, чтобы сохранить даже пустую строку при числовом DDL. SQL COPY/INSERT и PG не меняются. Для точного повторного импорта CSV хранится вместе с manifest; пакет с подпапками схем читается по путям manifest. Вычисление NULL-only использует уже имеющееся состояние inference, без дополнительного прохода по строкам и без растущего кеша.

Новая выдача использует `snp-anonymizer-csv-v2`: старый EXE безопасно откажется от неизвестной версии вместо молчаливой интерпретации NULL-only TEXT как пустой строки. Reader поддерживает v1 и v2; `empty_null_columns` имеет значение только в v2. В v1 прежние NULL/empty-правила сохраняются. Версии `.snpanon`, SQL и report.json не меняются.

Согласованность означает только согласованность предоставленного набора файлов. Проверить, что клиент выгрузил все CSV из одного snapshot, приложение без доступа к источнику не может. FK, master которого отсутствует, помечается `target_not_in_input`; исходные дефициты ссылок не скрываются.

Выдача появляется в новой папке после проверок; исходные файлы и существующие результаты не перезаписываются. Проект с исходными соответствиями запрещён внутри входной CSV-папки и результата. Публикация пакета не подразумевает копирование карты.

Опциональная карта замен в Excel (13.10.2026, `anonymizer-oiy`) — отдельный артефакт по явному пути пользователя, никогда не внутри пакета результата и не в report.json. Содержит домен, исходное значение и замену для каждой замены (схемы показаны финальными именами `snp_aNNNNNN`); содержит исходные значения и подлежит тому же режиму обращения, что проект. Память ограничена: поток из SQLite + write_only; ячейки длиннее 32 000 символов усекаются с маркером, управляющие символы вычищаются, при переполнении листа (1 000 000 строк) данные переносятся на следующий лист. Ошибка записи блокирует публикацию и откатывает карты.

Журнал проверок и ошибок (13.10.2026, `anonymizer-0k4`) — копится в памяти и выгружается в CSV только по явному запросу (кнопка GUI / `--log-csv`); в пакет результата и report.json не входит. Содержит стадии, технические имена, счётчики проверок «до→после» и обезличенные тексты ошибок; значений клиентов, путей источника и паролей не содержит. Файл пишется в конце прогона (включая неуспешный); сбой записи журнала не влияет на результат обработки.

Приёмка: синтетические COPY/INSERT/CSV, согласованные master/FK, UUID, числовые ключи, совпадающие коды разных сущностей, NULL/пусто/буквальный `\N`, кавычки/Unicode, дробная точность, JSON, ошибки формата, отмена, повторный проект, отказ от чужой отрасли, запрет путей вне CSV/staging, ограничение буферов по байтам и сквозной COPY около 1 ГиБ.

Восстановление в PostgreSQL не проверялось: экспорт проверяется синтаксически и повторным локальным разбором. Полный restore совместно с объектами платформы — отдельная интеграционная приёмка на предоставленном клиентском примере и целевой версии In.Plan.

## Импорт XLSX (28.10.2026)

Источник — отдельный `.xlsx`, плоская папка CSV/XLSX либо ZIP с файлами в корне или одной общей подпапке. Один файл соответствует таблице по имени файла (нижний регистр, удаление хвоста `_<12+ цифр>`); внутри ровно один лист с произвольным именем. Строка 1 — технические имена колонок. Дополнительные листы, объединения ячеек в области таблицы, формулы с кешем и без и Excel-ошибки отклоняются. Скрытые/отфильтрованные строки читаются. Повтор таблицы в нескольких файлах и XLSX вместе с manifest.json блокируют весь набор до чтения строк, независимо от режима пропуска ошибок.

Разреженные строки дополняются NULL; физически пустые строки пропускаются. Отсутствующая ячейка и явно пустой текст различаются; пустой текст сохраняется, кроме nullable NUMBER/INTEGER (NULL, как внешний CSV). Токен `\N` — NULL. Числовая XML-лексема сохраняется без float, формат отображения не применяется. Ведущие нули кодов следует хранить текстом; округление, выполненное Excel до импорта, невосстановимо. Поля DATE/DATE_TIME/TIME поддерживают ISO и числовые даты Excel 1900/1904 с точным Decimal-преобразованием; фиктивное 29.02.1900 и потеря точности запрещены.

Типы и бизнес-ключи берутся из того же metadata-only снимка; Store и проверки общие с CSV. `--csv-schema` задаёт исходную схему для XLSX; кодировка/разделитель к XLSX не применяются. Форматы проектов, отчёта и трёх экспортов остаются прежними. XLS/XLSB/XLSM, зашифрованные и защищённые книги не поддерживаются.

OOXML читается потоково, shared strings хранятся во временной SQLite с кешем, ограниченным байтами. Поле/строка ограничены 8 МиБ; распакованный архив — 4 ГиБ с проверкой заголовков и фактических байтов; каталог ZIP и метаданные также ограничены до накопления; ZIP64-каталог отклоняется до открытия ZipFile. Внешние источники и DTD/entities запрещены. Ошибка таблицы с включённым пропуском удаляет всю книгу, включая ранее записанные строки. Отмена, глобальные лимиты и неоднозначный состав набора прерывают прогон; временные данные удаляются.

## JSON-профиль

Подтверждён синтетической матрицей (`tests/test_json_profile.py`), 13.10.2026. JSONB-колонка возникает только из SQL DDL-входа: в снимке модели 0.2.0 таких колонок нет, поэтому для CSV-входа JSON недостижим. JSON в ключевой или FK-колонке блокирует обработку.

Сохраняются без изменений: числа (исходные лексемы, без `float`: `1e5`, `-0`, полная точность), `null`, булевы, ISO-даты и даты-время (`YYYY-MM-DD`, с `T` или пробелом; невалидный календарь вида `2026-13-40` заменяется как текст), пустая строка, пустые объект и массив, порядок свойств. Стандартные имена свойств сохраняются по явному списку (`qty`, `quantity`, `date`, `cost`, `price`, `item`, `loc`, `res`, `comp`, `key`, `value`, `name`, `description`, `data`, `values`, `rows`, `columns`, `properties`, `enabled`, `version`, `start`, `end`); остальные имена свойств заменяются детерминированно (домен на колонку, ординальный — одинаково между проектами). Строковые значения под свойствами `item`/`loc`/`res`/`comp` получают замену из тех же карт сущностей, что и одноимённые колонки таблицы: внутрь массивов имя свойства наследуется, вложенный объект распознаёт собственные имена свойств; ссылки под переименованным свойством не распознаются и заменяются как текст. Остальные непустые не-дата строки заменяются как текст. Если сгенерированная замена совпала с исходным текстом (имя свойства или значение), обработка блокируется с требованием другого проекта — та же политика, что для табличных текстов.

Форма значения нормализуется: компактный вывод без пробелов, `\u`-эскейпы декодируются до замены, повторные свойства схлопываются (остаётся последнее), порядок свойств сохраняется — в отличие от `jsonb`, ключи не сортируются. `NaN`/`Infinity` запрещены и блокируют обработку; битый JSON блокирует обработку с безопасной ошибкой. Значение JSONB обрабатывается целиком в памяти в пределах общего лимита поля 8 МиБ. Проверка сохранения (`json_data.signature`) сравнивает числа по лексемам, даты и структуру; корректность замены текста обеспечивается построением — инъективностью карты домена, отдельной сверки текста с картой нет.

Профиль семантики клиентских JSON-расширений (что означают нестандартные свойства) не согласован: замена может менять смысл расширения. Приёмка на реальном клиентском примере — отдельный шаг (карточка restore/клиентский контур), значения клиента не изобретаются.

## Загрузка в PostgreSQL

Опциональный шаг после всех проверок и файловых экспортов (13.10.2026, карточка anonymizer-es8). Источник данных — секции COPY подготовленного `dump.sql`: в базу попадают ровно те же transformed-строки, что в файловый пакет, с тем же экранированием и без `sys_id`. Одна транзакция: `CREATE SCHEMA IF NOT EXISTS` целевой схемы → проверка существования всех таблиц датасета в ней (отсутствующая — отказ, схему In.Plan приложение не реконструирует) → `TRUNCATE` только таблиц-источников одним оператором (`RESTART IDENTITY`, без CASCADE) → потоковый `COPY FROM STDIN` по таблицам → `COMMIT`. Любая ошибка — `ROLLBACK` и отказ от публикации пакета. Пароль не сохраняется и не попадает в отчёт; `report.json` содержит только `pg_load {schema, tables, rows}`. Конфликт имён таблиц между схемами датасета запрещён (все схемы маппятся в одну целевую). Интеграционная приёмка выполнена на локальном тестовом кластере (PG 16, порт 54329, синтетика); совместимость с реальным клиентским стендом и целевой версией In.Plan остаётся в карточке `anonymizer-10q`.

## Полный обход эталона (29.10.2026)

Явный `--bypass-model` / галочка GUI применяется ко всем таблицам входа. Эталон не обогащает структуру, BK/FK/ALIASES и именные эвристики отключены; дополнительные колонки остаются во входной структуре. Стандартный режим не меняется. CSV/XLSX автоматически определяют типы по полному потоку, сохраняя ограниченное состояние на колонку и строки на диске. XLSX использует нативные типы и числовые форматы дат; числовой текст остаётся TEXT. Несовместимые непустые типы дают ошибку таблицы. SQL/manifest используют собственные типы; data-only SQL без структуры отклоняется.

Обычные тексты заменяются без исключений для единиц, флагов, описаний и классификаторов. Числа (включая идентификаторы), булевы и даты сохраняются. sys_id очищается до NULL, update_date_time сохраняется как прочитано, change_author заменяется на snp. Домены текста изолированы префиксом режима и отдельны для schema/table/column; существование связей и уникальность ключей не подтверждаются. Отчёт явно отмечает неприменение модели и отсутствие проверки связей/ключей. JSONB из описанного SQL сохраняет числа/даты, заменяет клиентские строки без использования алиасов модели. Формат .snpanon сохраняется, повторные прогоны режима стабильны.

Новые замены обычных текстовых полей имеют вид `<имя_колонки>_000001`. При ограниченной длине поля сохраняется компактный base36-код; различимость между колонками в таком поле не гарантируется. Существующие соответствия проекта сохраняются, новые значения получают следующий номер в том же домене. Для полного перехода со старых подписей нужен новый проект. Формат замен UUID и внутренних строк JSON не меняется.

## Системные поля

В обоих режимах sys_id выдаётся как NULL в CSV и полном дампе; в data-only inserts.sql поле исключается из INSERT для работы default/identity существующей таблицы. update_date_time проходит без преобразования значения, change_author всегда равен snp (в том числе вместо пустоты/NULL). Исходные типы, длины, обязательность и ключи этих трёх полей не проверяются по значениям. Группы PK/UK/FK с системной колонкой на любой стороне пропускаются целиком. Декларации физических SQL-типов остаются в безопасной поддерживаемой грамматике. Выходной sys_id — nullable bigint, change_author — text; объявленный тип update_date_time сохраняется, при автоматическом вводе это TEXT. В XLSX для этих колонок сохраняется прочитанное представление ячейки, включая числовой Excel serial; формат отображения не применяется. Непригодное для целевого SQL-типа время не исправляется и может быть отклонено самой БД. Формулы, Excel-ошибки, структура файлов и лимиты по-прежнему проверяются.

При опциональной PG-загрузке очищенный sys_id исключается из заголовка и потока COPY; целевая БД назначает значение согласно своей структуре. Файловый NULL и сгенерированный идентификатор в PG — разные значения. Другие колонки передаются без изменений; транзакционность сохранена.

## Алфавит замен

Генерируемые текстовые значения, названия/описания и заменяемые строки/имена свойств JSON используют только ASCII-латиницу, цифры, пробелы и ASCII-разделители. Префиксы колонок, общие коды и UUID сохраняют формат. Неизменяемые исходные значения (включая кириллические единицы в стандартном режиме и сырой update_date_time) не транслитерируются.

Старые ASCII-mappings повторяются без перезаписи. Старые нелатинские mappings не меняются, но их использование блокируется безопасной ошибкой с требованием нового проекта. Проверка выполняется при чтении из SQLite/кеша и до записи новой замены; при экспорте карты её история проверяется потоково по одной записи. Кириллическое исходное old-значение в приватной карте допустимо, нелатинское new-значение не публикуется. Формат проекта и домены не меняются.
