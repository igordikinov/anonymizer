# GLM-002 — независимые группы PK/UNIQUE и бизнес-ключей

Состояние: **реализовано 13.10.2026 в сессии GLM поверх незакоммиченной GLM-001; независимые read-only reviewer и verifier (отдельные контексты) проверили все пункты; коммит ожидает авторизации пользователя**. Следует за согласованием группового metadata-контракта GLM-001.

## Результат (13.10.2026)

Дефект UNIQUE(a)/UNIQUE(b) воспроизведён до правок (одна сводная запись 0/0, дубликат a скрыт). Реализовано: каталог `key_groups` в Store — каждая DDL PK/UNIQUE группа отдельно (column-level и table-level, CREATE и ALTER ADD, дедуп повторов, `NULLS [NOT] DISTINCT` позиционным разбором хвоста; `UNIQUE INCLUDE` отклоняется явно) плюс логическая группа модели `model_bk` из YAML-флагов до слияния с DDL (sys_id исключён; явный grain колонками в отчёте). Проверка дубликатов по группам в SQLite `keyvals(gid,phase,body,n)` с канонизацией numeric/UUID/char; NULL в ключе не дублирует (PostgreSQL `NULLS DISTINCT`, PK-колонка с NULL по-прежнему отсекается как NULL в обязательном поле), `NULLS NOT DISTINCT` поддержан явно. Флаги `field["keys"]` и политика mapping не менялись. Manifest v1: опциональный `key_groups` (только DDL-группы), model_bk восстанавливается из снимка; строгая валидация внешнего входа. Порог сброса pending дополнен длиной key-буфера (5000 записей / 4 МиБ общий бюджет). По review: column-level UNIQUE/PK+REFERENCES сохраняют ссылку (ранний return убран), враждебный manifest (null/невалидные типы) даёт безопасную ошибку, `PRIMARY KEY ... NULLS ...` отклоняется как невалидный синтаксис. Замечено и задокументировано в README: составная группа с sys_id исключается из проверки без записи в отчёте.

Основание: `Validator.row` в `validation.py:98` собирает все поля, имеющие BK/PK/UK, в один общий tuple. Два независимых UNIQUE(a) и UNIQUE(b) не равны UNIQUE(a,b); дубликат a при разных b может быть скрыт. Дефект независимо воспроизведён при подготовке передачи. Флаги YAML без grouping не доказывают конкретный физический constraint.

Цель: хранить и проверять **каждую** исходную PK/UNIQUE группу отдельно на диске, а логический BK модели показывать с явно выбранным grain. Не выводить группы из похожих имён и не перенумеровывать quantities/flags из-за ошибочной PK-метки модели.

Приёмка: независимые UNIQUE(a)/UNIQUE(b); composite UNIQUE(a,b); PK с NULL; PostgreSQL NULL semantics, включая явное решение для NULLS NOT DISTINCT; канонические numeric/UUID; before/after duplicates по группе; byte-budget; manifest roundtrip; все старые тесты/EXE smoke. Unsupported semantics отклонять явно, а не выдавать PASS.

Ownership и разрешённые файлы определяет planner следующего этапа. Не считать эту карточку готовой реализацией или закрытым issue.
